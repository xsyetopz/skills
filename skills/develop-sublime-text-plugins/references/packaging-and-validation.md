# Package and test Sublime Text plugins

## Packed and loose packages

A [Sublime package][ref-sublime-package] is a ZIP with extension
`.sublime-package`, or a loose package directory. Loose files override matching
files in an installed archive. For a packed-artifact test, remove the old loose
implementation from the isolated profile; otherwise the test can silently
exercise the development copy instead of the archive.

Place modules, `.python-version`, command registrations, and resources at the
archive root. Avoid an extra outer directory. Use `sublime.load_resource` or
`load_binary_resource` for package resources; packed assets need not have normal
filesystem paths. Extract only when an external process genuinely needs a file,
and give the extraction a clear lifecycle. Do not assume `__file__` is a usable
resource directory.

Settings defaults belong in a named `.sublime-settings` resource. Preserve user
overrides instead of copying defaults over them. Only distribute settings,
menus, keymaps, and install/migration messages that the feature actually needs.
Never include generated bytecode, private files, or `package-metadata.json`;
Package Control generates that metadata when installing.

## Syntax and UI assets

Use the [Sublime syntax format][sublime-syntax-format] for grammars, not a
custom schema. Define appropriate scopes and contexts, and exercise
strings/comments, nesting, and embedded-language boundaries with host
syntax-test fixtures. YAML parsing does not verify scope stacks. Read the
syntax-test format and the target build's test runner before constructing
assertions or command names.

Escape untrusted text used in [minihtml][ref-minihtml] with a suitable HTML
encoder. Minihtml is not a browser DOM or a reason to introduce a web framework.
Check supported elements and URL behavior for the minimum host version rather
than copying webview code from another editor.

## Prove the relevant behavior

Record `sublime.version()` and the plugin host's `sys.version`. A successful
system-Python test does not prove package loading, command registration, edit
tokens, undo, settings reload, or packed imports.

Use [UnitTesting][ref-unittesting] for unittest cases inside Sublime. It
discovers `tests/test*.py` and supports the `unit_testing` command with a
`package` argument. Use its existing host runner before writing a bespoke
GUI-test protocol. For asynchronous tests, its deferred runner can wait for
conditions; do not sleep and assume a worker finished.

Run the command tests after loading and after reloading the package. For a
packed test, install the release archive and retain only tests as loose files.
Exercise the command palette separately when changing UI registration: direct
`run_command` tests do not establish menu visibility. Inspect console tracebacks
and test counts; an empty discovery result is not a successful behavior test.

Use a dedicated disposable profile or a verified headless test environment.
[Sublime safe mode][sublime-safe-mode] uses a separate data directory, **erases
it on each startup**, and requires other Sublime instances to be closed. Never
put important data there. Install test packages after starting safe mode, not
before the reset. Do not close a user's active editor to obtain a test
environment. The [CLI][ref-cli] documents `--safe-mode` and `--command`; there
is no general documented `--data-dir` switch to invent.

UnitTesting also provides a Docker runner. Check its current prerequisites and
pinned source before using it; lack of a running container daemon is not license
to modify the user's editor profile instead. Distinguish host execution, archive
inspection, and static checks in the final report.

## Package Control publication

Follow the [submission procedure][submission-procedure] and the channel
repository's current validation. First check for an existing package that
already provides the requested feature. A new package requires a specific
reason; the starter is an adaptation example, not a publication plan.

For GitHub/Bitbucket tag-based hosting, the package is rooted at the repository
root. Tags use SemVer, and the channel entry selects releases with `tags` plus
supported `sublime_text` and, when needed, platform constraints. Branch-based
releases are deprecated for new submissions. Derive the build selector from
actual tested API/runtime requirements, not the newest installed build alone.

Add the entry to the appropriate channel `repository/` file, run its current
checks, and submit only with authorization. Do not invent metadata keys from a
hosted release API: the centralized channel does not accept explicit `version`,
`url`, and `date` release fields used by manual hosting. A valid ZIP is not
registry acceptance, a published release, or proof of compatibility on all
platforms. Preserve the package's verified release source when updating it.

## Static-analysis stubs

Use [the bundled `.pyi` files](../assets/type-stubs) only when the target
project uses the API subset they describe.

These small `.pyi` files preserve the supplied repository's type information for
the API subset used by its example command. They are **partial**, not a complete
Sublime SDK or proof of runtime compatibility. Check additions against the
host's [API reference][api-reference].

When the target project already uses a type checker, copy these into its
configured stub directory or point its native `stubPath` setting at that
directory. Do not add a mandatory type checker solely for this fixture. Keep
stubs out of the packed runtime artifact. No mock `sublime.py` runtime module is
supplied: a mock could shadow the actual editor module or turn a missing host
into a false test pass.

Run the package's actual editor tests for edit lifetime, undo, selection, and
read-only behavior. Passing an offline type check is a separate result.
