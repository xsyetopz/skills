# Select a software development process from requirements

Identify where uncertainty resides: requirements, feasibility, integration,
operations, or coordination. Establish delivery cadence, team dependencies,
contractual obligations, reversibility, and existing practices. Do not infer a
regulated process from the industry name alone.

Default to the team's existing workflow plus the smallest correction for an
observed failure. For uncertain user behavior, use an early representative slice
and feedback. For uncertain technical feasibility, use a bounded experiment with
a discriminating result. For tightly coupled integration, integrate and test the
shared path early. For a fixed external acceptance contract, make traceability
and verification explicit without inventing approvals.

Distinguish a prototype that answers a question from production work that must
satisfy the full contract. Do not label an incomplete final deliverable an MVP
to avoid difficult requirements. A prototype's disposal or reuse is a decision,
not an assumption.

Choose Scrum, Kanban, staged delivery, or another named process only if the
request needs that choice. Explain which constraint the selected practices
address and what overhead they add. A label does not establish correctness,
predictability, or safety. Do not claim one methodology universally outperforms
another without relevant comparative evidence.

Return the selected practices, their triggers and exit conditions, and the few
alternatives rejected for concrete reasons. Keep tools, ceremonies, and roles
that the project actually needs; omit generic organizational transformation
advice.
